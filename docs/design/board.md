# 설계서: 병렬 에이전트 보드 (Board)

- 상태: 구현 대상(1·2단계). 3·4단계는 별도 설계 필요(9장).
- 대상: 데스크톱 앱(`karsenia-desktop`). 서버 `board` 연산은 웹이 나중에 같은 데이터를 쓰도록 함께 둔다. 웹 화면은 이번 범위가 아니다.
- 한 줄 요약: 흩어져 있는 채팅 상태, 변경량, 병합 가능 여부, 비용, 대기 질문, 이상 신호를 **읽기 전용 표 한 장**에 모은다. 보드는 승인·병합을 하지 않고 해당 채팅으로 보내기만 한다.

---

## 1. 문제와 목표

### 1.1 문제
worktree 채팅을 여러 개 돌리면 사용자는 (a) 어느 채팅이 내 답을 기다리는지, (b) 어느 채팅이 끝났고 병합할 만한지, (c) 어느 채팅이 헛돌거나 비용을 태우는지를 알려고 채팅을 하나씩 열어 봐야 한다. 사이드바는 상태와 대기 수만 보여 준다.

### 1.2 목표
| # | 목표 | 판단 기준 |
|---|------|-----------|
| G1 | 채팅 N개의 상태를 한 화면에서 파악 | 행 하나에 상태·진행·변경·병합·비용·신호가 보인다 |
| G2 | 내 입력이 필요한 채팅을 놓치지 않음 | 질문 대기 행이 항상 맨 위, 클릭 한 번에 해당 채팅 |
| G3 | 병합 가능한 채팅을 바로 구분 | 병합 칸이 `가능/충돌/뒤처짐/미커밋/없음/정리됨/확인 필요`로 나뉜다 |
| G4 | 이상 신호를 조기 발견 | 같은 호출 반복, 수정 파일 폭주, 가드 차단, 오래 걸림을 표시 |
| G5 | 열 개 넘는 채팅에서도 가볍게 동작 | git 프로세스 동시 3개 이하, 보드가 닫혀 있으면 git 작업 0 |

### 1.3 비목표 (의도적으로 하지 않는 것)
- 보드에서 권한 승인/거절, 병합, 정리(remove), 신뢰(`wt_trust`) 수락: 하지 않는다. 호스트는 사용자 대신 결정하지 않는다.
- 새 저장 파일: 만들지 않는다. 보드 데이터는 채팅 로그에서 계산하고 메모리에만 둔다.
- 채팅 내용(프롬프트, 도구 입력/출력)의 표시: 하지 않는다. 제목(마스킹)과 도구 이름만 쓴다.
- 웹 보드 화면, 계정별 한도 막대, 채팅 간 diff, 일괄 분배 생성: 이번 범위 밖(9장).

## 2. 현황 조사: 제안서의 전제와 실제

제안서는 "새로 만들 데이터는 거의 없다"고 했다. 코드를 확인한 결과는 다음과 같다. **이 표가 설계의 근거다.**

| 필요한 정보 | 제안서의 전제 | 실제 (코드 확인) | 설계 결정 |
|---|---|---|---|
| 상태, 대기 질문 수, wt 여부 | `SessionItem`에 있음 | 맞음. `Info{meta, state, pending}` (`src/session.rs:173`) | 그대로 사용 |
| 비용 | Deriver/Tab에 있음 | **채팅 단위 누적이 `Info`에 없다.** 액터가 `cost_chat`을 들고 있다. live `TurnEnd.cost_usd`는 프로세스 누적 원값이라 합산에 쓰면 안 된다(`src/costs.rs` 머리말). 로그의 `cost` 이벤트를 다시 접으면 옛 로그(cost 이벤트 없음)와 가져온 이벤트에서 틀린다(`restore_cost`, `session.rs:783`) | **`Digest`가 비용을 접지 않고** `Cmd::Board` 응답에 액터의 `cost_chat`을 그대로 담는다 |
| 도구 호출 수, 마지막 활동 | Deriver/Tab에 있음 | **둘 다 없다.** `Tab.last_ts`는 이름과 달리 생성 시각이다(`src/live/server.rs:196`). Deriver는 SSE 연결마다 새로 만들어져 라이브 보기를 연 동안만 존재한다(`server.rs:233`) | 액터에 상주하는 가벼운 `Digest`를 새로 둔다(3.1) |
| 이상 신호 | `watch.rs` | 맞음. 순수 함수형 감시기 `Watch`(`src/watch.rs`), "판단은 한 곳에서" 원칙 | `Digest`가 같은 `Watch`를 쓴다. 규칙 복제 금지 |
| worktree 변경량·병합 가능 | `facts()` | 맞음. 단 `wt_status`는 `facts()` 앞에 `verify(..., check_config=true)`를 거친다(`src/server/wt_ops.rs:55`). git 설정이 바뀌었으면 **보기만 해도** 거절한다 | 보드도 같은 `verify → facts` 경로. 우회 금지 |
| 상태 변화 이벤트 | "채팅 상태 변화 이벤트에 반응" | 레지스트리 수준의 채팅 목록 변경 이벤트가 **없다**(`registry.events`는 설정류만). 데스크톱은 이미 1.5초 폴링(`sessions_loop`) | 폴링 2초 + 캐시. 이벤트 신설은 하지 않는다 |
| 마스킹 | 라이브와 같은 규칙 | `live::mask::mask_text(text, limit)` | 제목에 그대로 사용 |

`facts()` 비용: git을 약 13회, 앞선 `verify`가 약 5회 더 실행한다(합계 약 18). 캐시도 동시 실행 제한도 없다. 락은 저장소별 `Mutex`뿐이고 `wt_status`는 락을 건너뛴다.

## 3. 아키텍처

```
  채팅 액터(채팅마다 1개)                         Registry                 데스크톱
 ┌───────────────────────────┐   Cmd::Board    ┌──────────────────┐  2초   ┌──────────────┐
 │ emit_at(envelope)         │ ──────────────▶ │ board()          │ ◀───── │ board_loop   │
 │   └ digest.feed(envelope) │  (Info,Digest)  │  ├ 채팅별 스냅샷 │        │ (보드가 열린 │
 │ digest: Digest (메모리)   │                 │  ├ FactsCache    │ ─────▶ │  동안만)     │
 └───────────────────────────┘                 │  │  due()? → 백  │  Rows  │ view::board  │
                                               │  │  그라운드 갱신│        │  필터·정렬·  │
                                               │  └ rows(now)     │        │  문자열 만듦 │
                                               └──────────────────┘        └──────┬───────┘
                                          Semaphore(3) ─▶ verify → facts          │ slint/board.slint
                                                                                  ▼ 클릭 → open-chat(sid)
```

원칙:
1. **계산은 순수 함수로**: `Digest::feed`, `merge_state`, `row`, `due`, 필터·정렬은 I/O가 없다. 시계는 `now`를 인자로 받는다. 테스트가 쉽다.
2. **보드 요청은 git을 기다리지 않는다**: `board()`는 항상 캐시로 즉시 답하고, 필요한 갱신만 백그라운드로 시작한다.
3. **보드가 닫히면 비용 0**: 별도 타이머가 없다. `Digest`는 처음 `Cmd::Board`를 받을 때 만들어지고(지연 생성, 3.1), git 갱신은 `board()` 호출(보드가 열려 있을 때의 폴링)이 일으킨다.
4. **새 저장 파일 없음**.
5. **기존 경로를 코드로 공유**: worktree 확인은 `worktree::verify → facts`만 쓴다(4.1).

### 3.1 `Digest` (새 모듈 `src/board.rs`)
채팅 로그의 이벤트를 **접어서(fold)** 만든 요약.

- **지연 생성**: 액터의 `digest: Option<Digest>`는 `None`으로 시작한다. 첫 `Cmd::Board`에서 `from_log(&self.log)`로 만들고, 그 뒤로는 `emit_at`이 `Some`일 때만 `feed`한다. 이유 둘: (a) `spawn()`이 액터를 만든 직후 `settle_restored()`가 `emit()`으로 이벤트를 쓰므로(`session.rs:476`, `:769`) 생성자에서 접으면 순서 문제와 이중 집계가 생긴다. (b) 앱 시작 때 모든 채팅 로그를 접는 비용(`Watch`는 도구 입력 전체를 정규 문자열로 만든다)을 보드가 닫혀 있으면 치르지 않는다. `self.log`를 바꾸는 곳은 `emit_at`의 push 하나뿐이므로(확인함) 이 방식이 안전하다.
- **가져온 이벤트(`imported: true`)**: `last_ts`에만 반영하고 나머지 카운터는 무시한다. `continue_as`/`fast_forward`로 만든 채팅이 원래 채팅의 턴·도구·반복·가드를 자기 것처럼 보이면 안 된다(기존 코드도 `UserTexts`, `restore_cost`에서 일관되게 뺀다).
- 같은 이벤트 열이면 같은 결과(재생=증분). 테스트로 고정한다.

| 필드 | 뜻 | 갱신 규칙 |
|---|---|---|
| `last_ts` | 가장 최근 이벤트 시각(ms) | `ts>0`인 모든 이벤트(가져온 것 포함)의 최댓값 |
| `run_ts` | 마지막으로 **실행 상태가 시작된** 시각 = 현재 일의 시작 | `state` 이벤트 `running`. (사용자 메시지가 아니라 상태 이벤트인 이유: 백그라운드 작업 종료로 `wake()`가 `Running`을 만드는 경로에는 `user` 이벤트가 없어 "오래 걸림"이 잘못 뜬다, `session.rs:1619`) |
| `turns` | 사용자 메시지 수 | `user` 이벤트(가져온 것 제외) |
| `tools` | 서로 다른 도구 호출 수 | `Watch::calls()` (`id` 중복 제거) |
| `turn_tools` | 이번 턴의 도구별 호출 수(상위 이름 계산용, 이름 64종 상한) | `user`에서 초기화 |
| `last_tool` | 가장 최근 도구 이름(80자 상한) | tool_use 블록 |
| `edited` | 수정한 서로 다른 파일 수 | `Watch::edited()` |
| `loops` | "같은 호출 반복" 경고 누적 수 | `Watch` 경보 `Loop` (서브에이전트·폴링 도구 규칙 그대로) |
| `scope` | 마지막으로 알린 수정 파일 폭주 단계(20 단위) | `Watch` 경보 `Scope` |
| `guarded` | 가드가 막은 도구 결과 수 | 라이브와 **같은 판정 함수** `live::derive::blocked(text)`(접두어 + `team`/`vhdb` 종류). 결과 텍스트는 판정 뒤 버린다 |
| `ctx` | 컨텍스트 `(마지막 최상위 assistant 호출의 입력·캐시·출력 합, 창 크기)` | 라이브 `Deriver`와 같은 규칙(`derive.rs:84`). 사용량의 누적 합이 아니다 |
| `last_ok` | 직전 턴 성공 여부 | `result` 이벤트(`num_turns==0` 무시), 새 `user`에서 `None` |

**비용은 `Digest`에 없다.** `Cmd::Board` 응답이 액터의 `cost_chat`을 `BoardSnap.cost`로 담는다(옛 로그 대체값과 가져온 이벤트 제외가 이미 `restore_cost`에 들어 있다. 판단은 한 곳에서).

`Watch`에는 읽기 전용 접근자 `calls()`, `edited()`만 추가한다. 경보 규칙은 건드리지 않는다. `derive.rs`는 `blocked(text)`를 `pub(crate)`로 빼고(두 곳이 함께 쓴다) `result_text`는 그 안에서만 쓴다.

비용 표기는 코드 전체 관례대로 **추정치**임을 밝힌다(`≈$0.42`).

**응답 크기**: 액터는 `Digest` 통째가 아니라 작은 `BoardSnap{info, counters, top_tool, cost, ctx, flags}`만 복제해 돌려준다(`Watch`의 `seen`/`files` 집합은 계속 커진다).

### 3.2 `Row` (보드 한 줄, 직렬화 가능)
`Info + Digest + FactsCache`를 합친 뷰 모델. 데스크톱과(나중의) 웹이 같은 JSON을 쓴다.

```
Row { sid, title(마스킹·80자), project(폴더 이름), account: Option<String>,
      worktree: bool, provider: bool, container: bool,   (겹칠 수 있다: 제공자 채팅도 worktree를 쓸 수 있다)
      state: running | idle | exited, pending, archived,
      last_ts, run_ts, turns, tools, top_tool: Option<(String,u32)>, last_tool,
      edited, loops, scope, guarded, cost, ctx_pct: Option<u8>, last_ok,
      wt: Option<WtRow{ merge: Merge, ahead, behind, files, insertions, deletions,
                        uncommitted, conflicts, age_ms, refreshing }>,
      signals: Vec<Signal> }
```

### 3.3 병합 상태 `Merge` (`merge_state(&Facts) → Merge`, 순수)
`Facts.blockers`(`missing`·`uncommitted`·`nothing`·`wrong_branch`·`main_dirty`·`mid_merge`·`conflict`)와 `behind`에서 **한 가지**로 정한다. 우선순위(위가 먼저):

| 순위 | 조건 | `Merge` | 표시 | 톤 |
|---|---|---|---|---|
| 0 | `wt.removed` | `Gone` | 정리됨 | 중립. **git을 실행하지 않는다**(`wt_status`도 removed면 `verify` 전에 거절한다, `wt_ops.rs:37`) |
| 1 | `facts.missing`, 또는 `verify`가 `not_owned`이고 읽기 전용 `can_forget`이 참(폴더를 손으로 지우고 prune함) | `Gone` | 정리됨 | 중립 |
| 2 | `blockers ∋ conflict` | `Conflict(n)` | 충돌 n | 나쁨 |
| 3 | `blockers ∋ uncommitted` | `Uncommitted(n)` | 미커밋 n | 주의 |
| 4 | `blockers ∋ wrong_branch/main_dirty/mid_merge` | `Blocked` | 막힘 | 주의 |
| 5 | `blockers ∋ nothing` | `Nothing` | — 변경 없음 | 중립 |
| 6 | 차단 없음, `behind>0` | `Behind(n)` | 가능 · 뒤처짐 n | 주의 |
| 7 | 차단 없음 | `Ready` | 가능 | 좋음 |
| — | 아직 계산 전 | `Unknown` | … | 중립 |
| — | `verify`가 `config_changed` | `UnsafeConfig` | git 설정 변경 | 나쁨 |
| — | `verify`가 `not_owned`(`can_forget` 거짓) | `UnsafeOwner` | 확인 필요 | 나쁨 |
| — | git 오류·시간 초과 | `Failed` | 확인 실패 | 주의 |
| — | worktree 아님 | `Na`(`wt=None`) | 해당 없음 | 중립 |

제안서 예시의 "뒤처짐 4"는 차단이 아니라 정보이므로 `Ready`보다 낮은 단계의 별도 표시로 두되 병합 가능함은 유지한다. 모든 상태는 **글자/기호가 함께** 나온다(색만으로 구분하지 않는다).

### 3.4 신호 `Signal` (이상·주의, 순수 계산)
| 신호 | 조건 | 비고 |
|---|---|---|
| `Ask(n)` | `pending>0` | 가장 강함 |
| `Loop` | `digest.loops>0` | `LOOP_AT=5` (`watch.rs`) |
| `Scope(n)` | `digest.scope>0` | 20개 파일 단위 |
| `Guard(n)` | `digest.guarded>0` | 가드 차단이 있었음 |
| `Long` | 실행 중이고 `now - run_ts ≥ 10분` | 상수 `LONG_MS`. 시각 역전·`run_ts=0`이면 무시. 백그라운드 작업이 깨운 실행은 그 시각부터 센다 |
| `Failed` | 유휴이고 `last_ok==Some(false)` | 직전 턴 실패 |
| `Ctx(pct)` | `ctx_pct ≥ 85` | 마지막 호출 기준으로 컨텍스트가 거의 참 |
| `Conflict` / `Behind` / `Unsafe` | 3.3의 병합 상태에서 파생 | 병합 칸과 중복 표시하지 않고 필터에만 쓴다 |

### 3.5 정렬·필터 (2단계, `src/view/board.rs` 순수 함수)
- 기본 정렬 "주의순": 순위 0 질문 대기 → 1 이상 신호(실행 중 포함) → 2 실행 중 → 3 병합 대상(충돌·막힘·가능) → 4 유휴 → 5 종료. 같은 순위 안에서는 `last_ts` 최신순. 안정 정렬.
- 다른 정렬: 최근 활동, 비용 높은 순, 이름순.
- 필터: 전체 / 질문 대기 / 실행 중 / 충돌·막힘 / 이상 신호.
- 보관한 채팅은 `view::panels::listed` 규칙(실행 중·질문 대기 중이면 보임)을 그대로 쓴다. **`Registry::board()`가 이 규칙을 먼저 적용하고 보이는 채팅에만 git 갱신을 예약한다**(숨은 보관 채팅에는 git이 돌지 않는다). 화면은 같은 규칙으로 다시 한 번 거른다.
- **계정**: 보드는 모든 계정의 채팅을 보여 준다(다른 계정에서 기다리는 질문을 놓치지 않는 것이 보드의 핵심 가치). 계정이 둘 이상이면 행에 계정 이름 칩을 붙인다. 사이드바의 계정 선택과는 독립이다.

## 4. git 호출 정책 (가장 중요한 위험 관리)

### 4.1 경로
행의 병합 정보는 **기존과 같은 경로**로만 만든다. 순서는 `wt_status`와 같다:
1. `wt.removed`이면 git 없이 `Gone` (`due()`도 부르지 않는다).
2. `Registry::worktree_root(repo, wt.root)`.
3. `worktree::verify(meta, root, check_config=true)`.
4. `worktree::facts(&owned)`.

보드 전용 git 코드는 없다.

- `verify`가 `config_changed`이면 `facts`를 **실행하지 않고** `Unsafe(config)`로 표시한다(채팅이 쓴 git 설정에 의해 보기만 해도 프로그램이 실행되는 것을 막는 기존 보안 규칙 유지). `not_owned`이면 읽기 전용 `can_forget`을 확인해 참이면 `Gone`, 아니면 `Unsafe(owner)`. 보드는 `wt_trust`를 부르지 않는다. 수락은 채팅의 기존 카드에서만 한다.
- **저장소 락**: 사용자가 한 번 누르는 `wt_status`는 락을 건너뛰지만, 자동 갱신은 그렇게 하면 안 된다. Windows에서는 실행 중인 프로세스의 작업 폴더를 지울 수 없어(`facts`가 worktree 폴더에서 `git status`를 실행한다) 자동 갱신이 `wt_remove`를 우연히 실패시킬 수 있다. 그래서 갱신은 `repo_lock(&repo).try_lock()`을 시도하고, **실패하면(병합·정리 중) 이번 갱신을 건너뛰고** 캐시를 유지한다. 성공하면 `verify+facts` 동안 락을 쥔다(같은 저장소의 갱신끼리도 직렬화된다).
- **결과 저장 직전 재확인**: 최신 `Info`를 다시 읽어 그 사이 `removed`가 되었거나 `cwd`/`config_hash`가 달라졌으면 결과를 버린다.
- `merge-tree --write-tree`(`facts`가 호출)는 원본 저장소에 tree 객체를 쓴다. 보드는 git 작업 폴더의 파일은 바꾸지 않지만 **저장소의 object 저장소에 loose 객체가 생길 수 있다**(7·13장).

### 4.2 캐시와 갱신 시점 (`FactsCache`, `due()` 순수 함수)
항목: `{result, computed_ms, seen_last_ts, seen_state, key:(config_hash, removed, cwd), fails, in_flight}`. `board()`가 행을 만들 때 보이는 worktree 채팅마다 `due()`를 물어 true면 백그라운드 갱신을 시작한다.

| 상황 | 갱신 조건 |
|---|---|
| 항목 없음 | 즉시 |
| `key`가 달라짐(`wt_trust`가 `config_hash`를 바꿈, removed, cwd) | **즉시**. 사용자가 채팅 카드에서 수락하면 보드가 180초 동안 낡은 `Unsafe`를 보이지 않게 한다 |
| 이미 갱신 중(`in_flight`) | 안 함(중복 제거) |
| 실행 중 | `last_ts`가 계산 이후 바뀌었고 **30초 이상** 지났을 때만. 8초 주기는 실행 중인 채팅이 git 설정을 쓰는 순간과 겹치는 틈(`verify`의 설정 검사와 `facts`의 git 사이)을 자동으로 반복해서 열고, 채팅 3개면 초당 약 7개 git이 뜬다 |
| 실행 중 → 유휴로 바뀜(`seen_state`≠현재) | 즉시 1회(막 끝난 채팅의 최종 변경량) |
| 유휴/종료, 새 이벤트 있음 | 계산 후 2초 이상 |
| 유휴/종료 | 180초 TTL(메인 브랜치가 움직이면 뒤처짐/충돌이 바뀐다) |
| 마지막 이벤트가 24시간 이상 전 | 30분 TTL |
| 이전 결과가 `Failed` | 60초 × 2^실패횟수, 최대 10분(git이 없거나 저장소가 사라진 채팅을 두드리지 않는다) |
| 이전 결과가 `Unsafe` | 60초마다 `verify`만 다시(비용이 작다). 위 `key` 변경은 즉시 |
| 사용자가 ↻ 누름 | 모든 항목 만료 표시. 단 채팅당 최소 5초 간격 |

### 4.3 동시 실행 제한과 보호
- 전역 `Semaphore(3)`: 갱신(verify+facts 한 묶음)이 동시에 3개까지. 나머지는 항목이 `refreshing`인 채로 대기한다. **보드 요청은 기다리지 않는다**.
- 20초 `timeout`은 **permit을 얻은 뒤의 구간만** 감싼다(대기열에 있던 일이 기다리다 `Failed`가 되지 않게). 초과하면 future를 drop해 `kill_on_drop`으로 git을 종료하고 `Failed`로 저장한다. 안쪽 git 한 번의 한도(30초)보다 바깥이 먼저 걸리는 것이 의도다.
- `in_flight`는 drop 가드로 풀어 panic·취소 뒤에도 남지 않게 한다.
- **보드를 닫은 뒤 대기열 정리**: permit을 얻은 직후 "마지막 `board()` 호출이 10초 이상 전이면 건너뜀"을 확인한다(보드를 닫아도 대기열의 수십 개가 실행되는 것을 막는다).
- `Registry::board(self: &Arc<Self>)`: 백그라운드 태스크가 `'static`이어야 하므로 `Arc`로 받는다(`wt_ops`도 `Arc`로 쓴다). 캐시 `Mutex`는 표준 `Mutex`이며 `await`를 넘겨 쥐지 않는다. 항목은 채팅이 삭제되면 `board()`에서 정리한다.
- **측정 계획**(구현 후 수행, 11장): worktree N개(1/5/12)에서 `verify+facts` 시간을 동시성 1/3/6으로 재서 상수(3, 30초, 180초)를 검증한다. Linux 수치만 얻을 수 있으므로 Windows는 수동 확인 항목이다.

### 4.4 남는 위험 (숨기지 않는다)
`SAFE_FLAGS`는 `core.fsmonitor`, 훅, 서명, rerere 등을 끄지만 **`filter.*.clean` 같은 설정은 막지 않는다**(`git status`가 실행할 수 있다). 기존 방어는 `verify`의 설정 지문 검사 하나다. 검사와 `facts`의 `git status` 사이의 시간 차(TOCTOU)는 사용자가 한 번 누르는 `wt_status`에도 있었는데, 보드는 이것을 자동으로 반복한다. 완화: 실행 중 채팅의 갱신 간격을 30초로 늘림, 설정이 바뀐 것이 보이면 즉시 `Unsafe`, 저장 직전 `config_hash` 재확인. **완전한 해결은 `facts`의 `status`가 필터를 못 쓰게 하는 별도 하드닝(예: `-c core.attributesFile`/`--no-optional-locks` 점검)이며 이번 범위 밖**이다. 이 한계는 NOTES와 최종 보고에 적는다.

## 5. 갱신 방식
- 데스크톱: 새 루프를 만들지 않고 **기존 `sessions_loop`(1.5초)** 가 "보드가 보이는 동안" 한 번 더 `registry.board()`를 부른다. 이미 있는 수명주기(이벤트·주기)를 쓰므로 루프 중복·누수 문제가 대부분 사라진다.
- **보이는지의 판단**: `side == 8 && !new-open`. (`side`만 보면 보드가 열린 채 새 채팅 폼을 열 때 `panel-open`만 불리고 `side`는 그대로라서 보이지 않는데도 갱신이 돈다.) Slint에서 `changed side`와 `changed new-open` 둘 다 Rust 콜백 `board-visible(bool)`을 부르고, 앱이 그 상태로 시작하는 경우를 위해 `init`에서도 부른다. Rust는 `AtomicBool`과 세대 카운터를 둔다. 보이게 된 순간 즉시 1회.
- 필터·정렬 변경은 서버를 다시 부르지 않고 마지막으로 받은 행으로 다시 그린다.
- `board()` 내부: 채팅마다 액터에 `Cmd::Board`(메모리 읽기)를 보낸다. `Registry::list()`처럼 순서대로 `await`하면 이벤트가 몰리는 채팅 하나(이벤트마다 동기 파일 쓰기)가 전체를 늦춘다. 그래서 `join_all` + 채팅당 300ms `timeout`이고, 시간을 넘긴 행은 캐시된 직전 스냅샷을 쓴다.
- 보드가 닫혀 있으면 호출이 없으므로 비용 0이다.
- 서버 `board` 연산(`{op:"board"}` → `{kind:"board", data:{rows:[…]}}`): 같은 `Registry::board()` 결과를 보낸다. 범위는 기존 `list` 연산과 같다(같은 소켓의 모든 계정 채팅). 웹은 나중에 이것을 쓴다.

## 6. 화면 설계 (데스크톱)

### 6.1 위치
사이드바 NavItem "보드"(⌥8)를 VHDB 다음에 추가한다. 전체 폭 대체 화면(`side == 8`, `x:280px`)으로, 기존 `TeamPage`·`VhdbPage`와 같은 방식이다. `page-name`에 이름을 추가한다. 이동은 `panel-open(8)` → 보드 루프 시작, 다른 페이지로 가면 중지.

### 6.2 와이어프레임 (넓이 1000px 기준)
```
┌ 보드 ─────────────────────────────────────────────────────────────────────────┐
│ 실행 2 · 질문 대기 1 · 병합 가능 3 · 합계 ≈$1.83        [전체 ▾][주의순 ▾] [↻] │
├───────────────────────────────────────────────────────────────────────────────┤
│ 상태      채팅                진행              변경           병합      비용   │
│ ⏸ 질문 1  add-search  Work    권한 대기 1건     +310 −40 (9)   ⚠ 충돌 2  ≈$1.10 │
│ ▶ 실행    fix-login           Edit×12 · 4분     +120 −8 (5)    ✓ 가능    ≈$0.42 │
│ ▶ 실행 ⚠  migrate-db          Bash×30 · 14분    +12 −0 (2)     ⏳ 뒤처짐 4 ≈$0.88 │
│           같은 호출 반복 · 오래 걸림                                              │
│ ✔ 끝남    refactor-db         2분 전            +80 −90 (3)    ✎ 미커밋 1 ≈$0.31 │
│ ✔ 끝남    notes               1시간 전          해당 없음      해당 없음  ≈$0.05 │
└───────────────────────────────────────────────────────────────────────────────┘
```
- **상태**: 질문 대기(`pending>0`) > 실행 > 끝남(유휴) > 종료(프로세스 종료) > 실패(마지막 턴 실패). 글자와 기호를 함께 쓴다.
- **채팅**: 제목(마스킹), 프로젝트 폴더 이름(보조 줄), 계정 칩(계정 2개 이상일 때).
- **진행**: 질문 대기 중이면 "권한 대기 n건"; 실행 중이면 `상위도구×횟수 · 경과`; 유휴면 "n분 전"(`last_ts` 기준). 신호가 있으면 둘째 줄에 문구로 나열.
- **변경**: `+삽입 −삭제 (파일 수)`. 계산 전이면 `…`, worktree가 아니면 `해당 없음`. 데이터가 오래됐으면(`age_ms>TTL`) 흐리게.
- **병합**: 3.3의 표시. worktree가 아닌 채팅은 칸을 비우지 않고 **"해당 없음"**을 명시해 worktree 전용 화면처럼 보이지 않게 한다.
- **비용**: `≈$`. 합계는 상단 요약.
- 행 높이 고정(신호 줄이 있으면 2줄), 목록은 스크롤. 좁은 폭(<760px)에서는 "변경" 칸을 숨긴다.

### 6.3 상호작용
- 행 클릭 = 해당 채팅 열기(`side=0`, 새 채팅 폼 닫기, `open-chat(sid)`). 질문 대기 행도 같은 동작이며 채팅 화면에서 권한 카드가 이미 보인다.
- 병합 칸을 눌러도 같은 동작(채팅 열기)이다. 변경 보기·병합 점검은 채팅의 기존 worktree 카드(`wt_status`/`wt_merge`)에서 한다. 보드는 **승인·병합 버튼이 없다**.
- 키보드: 위/아래로 행 이동, Enter로 열기(Slint `FocusScope`). 기존 `refocus()`는 `side≠0`이면 채팅 키 입력창으로 포커스를 보내므로(`app.slint:255`) **`side==8` 분기를 추가해 보드의 `FocusScope`에 포커스를 준다.** 그렇지 않으면 방향키·Enter가 동작하지 않는다. 접근 가능한 이름은 상태+제목+병합 문구를 합쳐 만든다.
- 연결 지점(빠뜨리기 쉬운 곳): `page-name` 삼항 연쇄(`app.slint:107`)의 기본값은 설정이므로 `side==8` 분기를 넣지 않으면 "설정"으로 표시된다. ⌥ 단축키 블록(`app.slint:276`)에 `"8"`을 추가한다.
- 빈 상태: "진행 중인 채팅이 없습니다. 새 채팅에서 작업 트리 사용을 켜면 여기에 모입니다."

### 6.4 다국어
`src/view/i18n.rs`의 `TABLE`에 `board_*` 키(ko/en)를 추가한다. 상태·병합·신호 문구와 시간 표기(방금/분/시간/일 전)를 포함하며 Rust에서 문자열을 만들어 Slint에는 완성된 텍스트를 넘긴다(Slint는 표시만).

## 7. 보안·프라이버시
- 행에 나오는 텍스트는 **제목(`mask_text`, 80자)**, 도구 이름(80자), 폴더 이름, 숫자뿐이다. 프롬프트·도구 입력·출력·충돌 파일 이름은 보드에 싣지 않는다(파일 이름은 기존 카드에만).
- `Digest`에는 비밀이 될 만한 원문을 저장하지 않는다. 도구 이름과 카운터만 유지한다. 가드 차단 판정은 결과 텍스트의 **접두어 비교만** 하고 텍스트는 버린다.
- git 안전 설정(훅·외부 diff·프롬프트 끔, `GIT_*` 제거)과 `verify` 보안 검사를 우회하지 않는다.
- `board` 연산은 호스트의 **상태를 바꾸는 동작이 없다**(채팅·설정·파일 변경 없음). 다만 `facts`의 `merge-tree --write-tree`가 원본 저장소에 git 객체를 쓸 수 있으므로 "git에 아무것도 쓰지 않는다"고는 말하지 않는다(4.1).
- 서버 `board` 연산의 인증·범위는 기존 `list`와 같다(같은 소켓).

## 8. 오류·예외 처리
| 상황 | 동작 |
|---|---|
| 채팅 액터가 사라짐(삭제 중) | 그 행을 건너뛴다 |
| `ts==0`인 옛 로그 | `last_ts` 0 → 진행 칸 "—" |
| 시계 역전(`now<turn_ts`) | 경과 0, `Long` 아님 |
| worktree 폴더가 사라짐(`missing`) | `Gone`(정리됨) |
| 원본 저장소 이동/삭제 | `verify` 실패 → `Failed` 또는 `Unsafe`, 크래시 없음 |
| git 없음/오래됨(`merge-tree` 미지원) | `facts` 오류 → `Failed` ("확인 실패"), 다음은 TTL |
| 채팅이 수백 개 | 채팅 수만큼 메모리 왕복만 하고 git은 세마포어로 제한. 오래된 채팅은 30분 TTL |
| 질문 대기이지만 프로세스가 죽음 | `state=exited`가 우선(끝남이 아니라 "종료") |
| 보관한 채팅 | `listed` 규칙을 따른다. 숨겨진 채팅에는 git도 돌지 않는다 |
| 백그라운드 작업이 실행을 다시 깨움 | `run_ts`가 그 시각이라 `Long`이 오탐하지 않는다 |
| 가져온(`imported`) 이벤트만 있는 새 채팅 | 카운터 0, `last_ts`만 있음 |
| 사용자가 카드에서 `wt_trust` 수락 | 캐시 `key`의 `config_hash`가 바뀌어 다음 폴링에서 즉시 재확인 |
| 병합·정리가 진행 중(저장소 락 보유) | 이번 갱신을 건너뛰고 캐시 유지 |
| 한 채팅의 액터가 느림 | 300ms 뒤 그 행은 직전 스냅샷 |

| 2 | 정렬·필터, 이상 신호(반복·폭주·가드·오래 걸림·실패·컨텍스트), 오래 걸림 강조 | **구현** |
| 3 | 같은 작업을 여러 worktree 채팅에 한 번에 나눠 주기 | 미구현. 별도 설계 필요 |
| 4 | 채팅 간 diff 비교 | 미구현 |

3·4단계를 하지 않는 이유와 선행 조건(스케치):
- 3단계는 보드가 아니라 **채팅 생성 흐름**의 변경이다. 필요한 결정: 배치 묶음 식별자(`Meta`에 배치 id를 둘지), 동시에 시작할 개수 제한과 계정 한도(`usage.rs`) 반영, 총 비용 상한, 실패한 한 개가 나머지에 주는 영향, 같은 프롬프트로 N개를 만들 때의 권한 모드 안전 규칙(기억된 기본값 정책과 충돌 금지). 보드가 있어야 결과를 모아 볼 수 있으므로 1·2단계가 선행 조건이다.
- 4단계는 같은 작업을 나눴을 때만 의미가 있어 3단계 뒤에 한다. 방식은 두 브랜치의 `git diff --stat`을 같은 안전 경로로 읽기만 하는 것이다.
- 계정별 한도 막대(제안서의 차별점)는 `usage.rs`의 `UsageStore::snapshot()`이 있어 얹기 쉽지만, 이번에는 행·요약에 넣지 않는다. 2단계 이후 별도 소규모 작업으로 둔다.

## 11. 테스트·검증 계획
### 11.1 자동 테스트
- **단위(`src/board.rs`)**: `Digest` — 재생과 증분이 같은 결과, **`settle_restored`가 낸 이벤트 뒤에 지연 생성한 것과 처음부터 증분한 것이 같음**, `user`에서 턴 카운터 초기화, 중복 `id` 한 번만 집계, 반복 5회 경보, 서브에이전트 호출, 가드 판정(접두어와 `team`/`vhdb`), `num_turns==0` 무시, `ts==0` 처리, **`imported` 이벤트는 `last_ts`만 바꿈**, **`user` 없이 `state: running`만 온 경우 `run_ts`가 그 시각(`Long` 오탐 없음)**. `merge_state` — 3.3의 모든 우선순위 조합. `due` — 실행 중(30초·`last_ts` 변경 조건)/막 끝남/TTL/오래됨/중복 갱신/강제 새로고침 간격/**`config_hash`·`removed` 변경 시 즉시**/`Failed` 지수 백오프/`Unsafe` 60초. `signals` — 각 조건과 경계(10분, 85%).
- **단위(`src/view/board.rs`)**: 정렬 순위·안정성·필터·요약 줄·시간 표기·계정 칩 규칙·`listed` 준수.
- **통합(`tests/board.rs`)**: 가짜 claude로 채팅 생성 → `registry.board()`가 상태·도구 수·비용을 돌려줌, 질문 대기가 `pending`으로 나옴, worktree 채팅에서 `Ready`/`Conflict`/`Uncommitted`가 실제 git으로 계산됨, git 설정을 바꾼 worktree가 `Unsafe`이고 `facts`가 실행되지 않음, **`removed`이면 git 0회**, **저장소 락이 잡혀 있으면 갱신을 건너뜀**, **보관한 채팅에 git이 돌지 않음**, **보드를 닫은 뒤 대기열 작업을 건너뜀**, 갱신이 세마포어 상한을 넘지 않음, 느린 액터 한 개가 응답을 300ms 넘게 붙잡지 않음, WebSocket `board` 연산 응답.
- **회귀**: 기존 전체 테스트, `node --test tests/ui.test.mjs`, clippy(기준선 22 유지), Windows 교차 `cargo check`.
- **스크린샷**: `examples/shots.rs`에 보드 장면 추가(넓음/좁음, 어두움/밝음, 빈 상태, 신호 줄 포함). 사람이 모양을 확인한다.

### 11.2 부하 측정 (구현 후 실제로 잰다)
무시(`#[ignore]`) 테스트 `board_load`로 한 프로젝트의 worktree 채팅 1/5/12개를 처음 확인하는 데 걸리는 시간을 재고 결과를 12장에 기록했다. 기준: 12개 채팅의 전체 갱신이 20초 안, 동시 git 프로세스가 3개를 넘지 않음. (같은 저장소의 확인은 줄을 서므로 동시성 1/3/6 비교는 하지 않았다. 여러 저장소를 동시에 보는 경우와 loose 객체 증가량은 측정하지 않았다.)

### 11.3 Windows 수동 확인 목록 (자동 테스트 없음)
1. 보드 열기/닫기, 단축키 ⌥8, 다른 페이지 이동 시 루프 중지.
2. 질문 대기 행 클릭 → 해당 채팅의 권한 카드.
3. worktree 채팅 3개 이상에서 병합 칸이 맞는지, 보드를 열어 둔 동안 CPU/프로세스 수.
4. 긴 경로, 한글 제목, 계정 2개 이상, 보관한 채팅이 규칙대로 보이는지.
5. Trend Micro 실시간 검사가 켜진 상태에서 갱신 지연이 허용 범위인지.
6. **보드를 연 상태에서 `wt_remove`(정리)가 성공하는지**(Windows는 실행 중 프로세스의 작업 폴더를 지울 수 없다).
7. 보드가 열린 채 새 채팅 폼을 열었다 닫을 때, 그리고 ⌥8을 빠르게 반복할 때 갱신이 겹치거나 멈추지 않는지, 방향키·Enter가 동작하는지.

## 12. 측정 결과와 한계

### 12.1 부하 측정 (`cargo test --test board -- --ignored --nocapture board_load`)
환경: Linux, SSD, git 2.53, 작은 저장소(파일 1~13개), 한 프로젝트의 worktree 채팅 N개. 값은 `settled()`가 100ms마다 확인한 값이라 해상도는 약 0.1초다.

| 채팅 수 | 첫 갱신(모두 한 번씩 확인) | 이미 신선할 때의 `board()` 호출 |
|---|---|---|
| 1 | 0.10초 | 약 30µs |
| 5 | 0.20초 | 약 70µs |
| 12 | 1.23초 | 약 140µs |

- 같은 저장소의 채팅은 한 줄로 서서 하나씩 확인되므로(4.3) 위 값이 곧 "한 번에 git 하나"의 처리 속도다(채팅당 약 0.1초, git 약 18회).
- 기준(12개 채팅의 전체 갱신 20초 이내, 동시 git 3개 이하)을 만족한다. 단 **작은 저장소의 Linux 값**이다. 큰 저장소, 느린 디스크, Windows(Trend Micro 실시간 검사 포함)에서는 같은 18회 git 호출이 몇 배 느릴 수 있다. 그 경우에도 보드 요청은 기다리지 않고 캐시로 답하므로 화면이 멈추지는 않고 병합 칸이 `…`로 더 오래 남는다.
- 측정하지 않은 것: `merge-tree --write-tree`가 만드는 loose 객체의 증가량, 큰 저장소에서의 갱신 시간, Windows. 값을 얻으면 이 표에 추가한다.

### 12.2 알려진 한계 (최종 보고에도 적는다)
1. 4.4의 설정 검사와 `git status` 사이의 틈은 줄였을 뿐 막지 못했다(`filter.*.clean`은 git 호출 플래그로 꺼져 있지 않다). 완전한 해결은 `facts`의 `status`를 하드닝하는 별도 과제다.
2. 웹 화면은 없다(`board` WebSocket 메시지만 있다).
3. Windows는 직접 확인하지 못했다(11.3 목록).
4. 병합 칸을 눌러도 워크트리 카드가 자동으로 열리지는 않는다. 채팅을 열 뿐이고 카드는 헤더의 기존 칩으로 연다.
5. 행의 키보드 이동은 방향키와 Enter만이고, 스크린 리더 동작은 확인하지 못했다.

| 위험 | 대응 |
|---|---|
| `facts()` 비용 미측정 | 세마포어 3, TTL 정책, 측정 테스트로 상수 검증(11.2) |

| 보드가 worktree 전용 화면처럼 보임 | 일반 채팅을 항상 포함, 병합 칸 "해당 없음" 명시 |
| 보드가 사용자 대신 결정한다는 오해 | 쓰기 버튼 없음, 클릭은 이동만 |
| 이상 신호 규칙이 화면마다 갈라짐 | `Watch` 한 곳 재사용, 보드는 읽기만 |

| `merge-tree --write-tree`가 loose 객체를 쌓는다 | 갱신 간격을 길게 유지하고 보드가 닫히면 중단. 앱의 git 호출은 `gc.auto`를 끄므로 쌓일 수 있다. **증가량은 측정하지 않았다**(12.1) |
| 경쟁 앱과 겹침 | 가드 차단·권한 대기·비용·`config_changed` 안전 표시를 보드의 차별점으로 유지, 계정 한도는 다음 작업 |
